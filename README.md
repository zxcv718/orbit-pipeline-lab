# Orbit Pipeline Lab

공개 궤도 데이터로 **"정해진 시각에 전체를 다시 계산하는 파이프라인"과 "데이터가 바뀔 때 바뀐 만큼만 계산하는 파이프라인"의 차이**를 직접 재본 실험.

우주 물체 근접 분석(conjunction assessment)처럼 대용량 궤도 데이터를 주기적으로 처리하는 시스템에서,
스케줄링 방식이 데이터 신선도·계산량·서비스 일관성에 얼마나 영향을 주는지 수치로 확인하는 것이 목적이다.

> 특정 회사의 시스템을 재현한 것이 아니다. 모든 입력은 공개 데이터이고, 모든 수치에는 측정 조건과 한계를 함께 적었다.

## 신선도는 세 조각의 합이다

```
데이터 나이 = 원천 요소 나이  +  수집 지연        +  처리 지연
              (중앙값 22.9h)     (일1회: 평균 12h)   (전파·스크리닝·게시)
              통제 불가          통제 가능           통제 가능
```

수집 주기를 하루 1회에서 2시간마다로 줄이면 두 번째 항의 기댓값이 12시간에서 1시간으로 줄어든다.
첫 번째 항은 줄지 않는다. 그래서 "자주 받으면 다 해결된다"는 말은 과장이다.

## 파이프라인

```
수집 → 검증(OMM·6자리 번호) → 변경 감지(지문 비교) → 전파(SGP4) → 근접 후보 스크리닝 → 게시 → 관측
```

같은 코드에 정책만 두 가지로 둔다.

| | 시간 기반 (비교군) | 데이터 기반 (제안) |
|---|---|---|
| 트리거 | 매일 고정 시각 | 갱신 주기마다 수집, **변경이 있을 때만** 하류 실행 |
| 계산 범위 | 전체 재계산 | 바뀐 객체와 그 객체가 낀 쌍만 |
| 게시 | 통째로 지우고 다시 채움 | 새 버전에 다 쓴 뒤 한 번에 교체 |
| 실패 | 그대로 진행 | 재시도(단, 403은 금지) · 직전 스냅샷 폴백 · 신선도 경보 |

## 데이터 이용 정책 준수

[CelesTrak 이용 정책](https://celestrak.org/usage-policy.php)을 지키는 것이 이 실험의 전제다.

- GP 데이터는 2시간마다 갱신되고, **갱신당 1회만** 내려받는다 (스크립트가 자체 게이트로 강제)
- 200이 아닌 응답을 받으면 **즉시 멈추고 재시도하지 않는다**. 하류는 직전 스냅샷을 쓴다
- CSV 포맷을 써서 하루 전송량을 100MB 아래로 유지한다
- `celestrak.org`만 사용한다 (`.com`은 301)

## 재현

```bash
python3 collect/fetch_gp.py        # 스냅샷 1개 수집 (2시간 내 재실행은 자동으로 건너뜀)
python3 analyze/snapshot_stats.py  # 6자리 번호 객체 수, 요소 나이 분포
python3 analyze/diff_snapshots.py  # 직전 스냅샷 대비 변경 비율, 쌍 기준 절감 추정
python3 site/build_site.py         # 정적 대시보드 생성
```

궤도 전파에는 `sgp4`가 필요하다. **Python 3.12를 쓴다** — 3.14에서는 C++ 가속이 꺼진 채로 설치돼
전파 비용 측정이 왜곡된다(로컬 실측: 3.12 `accelerated=True`, 3.14 `False`).

```bash
uv run --python 3.12 --with sgp4 python analyze/propagate_bench.py
```

## 한계

- EPOCH는 발행 시각이 아니라 궤도 상태의 기준 시각이다. "언제 게시됐나"와는 다르다.
- 근접 스크리닝은 단순화한 버전이다. 정밀 충돌 확률 계산이 아니라 **계산 부하를 보기 위한 대리 지표**다.
- CelesTrak의 갱신 주기(2시간)는 다른 데이터 제공처와 다르다. 여기 수치를 다른 시스템에 그대로 옮길 수 없다.
- 원본 스냅샷은 용량 때문에 레포에 보관하지 않는다. 파생 결과(원장·통계·변경 인덱스)만 남긴다.
- 2026-09-14 00:30 UTC 이전 실행분은 예약 시각을 2시간 슬롯으로 계산하던 버그 때문에 `data/manifest.jsonl`의 `scheduled_at`이 최대 1시간 이르게 기록됐다. 지연 분석(`analyze/live_summary.py`)은 이 필드 대신 실제 시작 시각이 속한 매시 슬롯으로 다시 계산한다.
